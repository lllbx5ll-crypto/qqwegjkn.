# NEXBOTS — التحديث الموحّد: الخاص والستوريات والبيع

هذه ملفات **المشروع الكامل** وليست صفحة تجريبية. حافظنا على تصميم NEXBOTS الموجود وواجهاته الأساسية. لا يظهر رقم الإصدار على الموقع؛ يمكن معرفة الإصدار داخلياً عبر `/api/health` عند تشخيص أي عطل.

## ما أُضيف

- **الخاص والستوريات** من القائمة: ستوريات عامة تظهر حتى لغير المتابعين، بصور المستخدمين ضمن دوائر؛ النص والصورة وفيديو MP4 لا يتجاوز **15 ثانية**؛ عرض وإعجاب وإلغاء إعجاب وعدد المشاهدات لصاحب القصة، وحذف يدوياً. **النشر للمشتركين النشطين والمالك فقط**؛ باقي الأعضاء المسجلين يمكنهم المشاهدة.
- **الانتهاء والحذف الحقيقي:** كل قصة لها `expiresAt` من نوع Firestore Timestamp لمدة **24 ساعة**؛ تختفي وتتعطّل وسائطها فور انتهاء المدة. ملف وسائط الستوري يوضع في R2 تحت `stories/<id>/media`، وسجل القصة وتفاعلاتها في Firestore. عامل التنظيف المجدول يحذف الثلاثة من التخزين والبيانات تلقائياً في التشغيل التالي (كل 15 دقيقة تقريباً، مع احتمالات تأخير بسبب الخدمات). **حذف القصة يدوياً يحذف ملف R2 والسجل فور نجاح العمليتين**، وتُزال التفاعلات المتبقية عند انتهاء مدتها.
- **حفظ المساحة:** عامل التنظيف لا يمس صور البروفايل أو ملفات المشاريع؛ يزيل وسائط `stories/` فقط، ثم يحذف سجلات `storyViews` و`storyLikes` و`stories` المنتهية.
- **المراسلات الخاصة**: بحث مطابق لـ `@username` فريد (من 3 إلى 24 حرفاً إنجليزياً صغيراً/رقماً/شرطة سفلية)، بدء محادثة، روابط HTTPS قابلة للفتح بأمان، حالات «لم تُقرأ» و«تمت القراءة»، حظر وإلغاء حظر؛ لا تُقبل رسائل جديدة بين طرفين توجد بينهما حالة حظر، مع بقاء السجل القديم.
- **البلاغات**: مستخدم يبلغ عن مستخدم، يظهر البلاغ لصاحب صلاحية إدارة الأعضاء، مع زر إيقاف الحساب ورفع الحظر، ورسالة الدعم بالبريد عند الحظر.
- **مشاريع للبيع للمشتركين**: يحدد صاحب المشروع عند رفعه السعر بالدولار؛ المشروع يمر بمراجعة الإدارة كالسابق. لا يفتح الملف المدفوع ولا رابط تنزيله لمن لا يملك إذن الشراء. الدفع **خارج الموقع وبشكل يدوي**، ثم يمنح البائع أو الإدارة إذن التحميل للمشتري بمعرّف UID أو `@username`. لا توجد بوابة دفع آلي.
- **تعديل وحذف المشروع**: يستطيع صاحب المشروع حذفه؛ تعديله يصبح طلباً في لوحة الإدارة حتى تتم الموافقة عليه أو رفضه. المالك يستطيع تعديل أو حذف أي مشروع مباشرة. صلاحيات الاشتراكات ورفع الملفات السابقة محفوظة.

## ضروري عند التثبيت — بالترتيب

### أولاً: انشر قواعد Firestore قبل الموقع

1. ادخل إلى Firebase Console → مشروع **exbots** → Firestore Database → **Rules**.
2. افتح الملف **`firestore.rules` الموجود بجذر هذا المشروع**، وانسخه بالكامل إلى المحرّر، ثم **Publish**.
3. هذه القواعد تعمل باستخدام Firebase ID Token؛ **لا تحتاج Service Account أو مفتاحاً خاصاً**. لا تستخدم قواعد النسخ القديمة.
4. اختبار القواعد الحي يحتاج مستخدمين تجريبيين، لأن نجاح فحص JavaScript وحده لا يثبت قبول قواعد Firestore.

### ثانياً: حدّث موقع Cloudflare Pages

1. افتح ZIP وانسخ **محتوياته** إلى جذر مستودع GitHub `NEXBOTS` في فرع `main`. لا تضع مجلداً خارجياً إضافياً فوق `src` و`public` و`server` و`functions` و`package.json`.
2. اعمل **Commit / Push**. Cloudflare Pages المتصل بالمستودع يبني الموقع تلقائياً؛ إعداداته كما سبق: React (Vite)، `npm run build`، مجلد `dist`.
3. تأكد أن `/api/health` يعرض `version: v2.0.0`، ثم افتح الصفحة الرئيسية. رقم الإصدار **مخفي من واجهة الزوار** عمداً.
4. ربط R2 الحالي يبقى `FILES` → `nexbots-files`؛ لا تنشئ Bucket جديداً ولا تضع أسرار R2 في GitHub.

### ثالثاً: فعّل عامل حذف الستوري التلقائي (مطلوب مرة واحدة)

**مهم:** مجرد رفع GitHub أو نجاح Pages **لا يشغّل مهام الحذف المجدول**. Cloudflare Pages يحدّث الموقع فقط؛ عامل التنظيف في مجلد `cleanup/` يحتاج نشر Worker صغير منفصل في **نفس حساب Cloudflare ونفس مستودع المصدر**.

من الكمبيوتر الذي عليه Node.js، داخل **جذر المشروع**:

```bash
npm install
npx wrangler login
npx wrangler deploy --config cleanup/wrangler.toml
```

وافق على ربط حساب Cloudflare. ينشئ الأمر Worker باسم `nexbots-story-cleaner`، ويربط له مساحة R2 نفسها `nexbots-files` ويشغّله بجدولة `*/15 * * * *` (كل 15 دقيقة). داخل `/cleanup/wrangler.toml` يوجد **مفتاح Firebase Web API عام** فقط، وليس مفتاحاً إدارياً. اترك الكود كما هو. للتحقق: Cloudflare → Workers & Pages → `nexbots-story-cleaner` → **Triggers**، تأكد من وجود Cron Trigger، ثم راقب Logs / Observability بعد تشغيله. إن لم تنشر هذا العامل، **ستختفي الستوري من الموقع بعد 24 ساعة، لكن لا تضمن حذف السجلات والوسائط من الخدمات تلقائياً**.

#### حماية إضافية لملفات R2 (اختيارية وننصح بها)

من Cloudflare → R2 Object Storage → `nexbots-files` → Settings → **Object Lifecycle Rules**، أضف قاعدة حذف بعد يوم واحد **مع شرط Prefix يساوي `stories/` فقط**. إذا تعذر وضع شرط البادئة، **لا تحفظ القاعدة**؛ لأن تطبيقها على كل الـBucket سيحذف ملفات المشاريع وصور الأعضاء. قواعد دورة الحياة تعمل بوقت تقريبي، لذا تبقى مهمة التنظيف المجدولة هي المسؤولة عن حذف سجلات Firestore أيضاً.

### رابعاً: جرّب بالترتيب

1. ادخل بحسابك المالك وحساب عضو مجاني وحساب مشترك نشط.
2. تأكد أن المجاني يشاهد القصص ولا يستطيع نشرها، والمشترك ينشر نصاً وصورة وMP4 لا يتجاوز 15 ثانية.
3. جرّب فيديو أطول من 15 ثانية: يجب رفضه، وجرّب حذف قصة منشورة، ثم راجع `stories/` في R2.
4. أنشئ `@username` مختلفاً لكل حساب. ابحث عن الثاني، أرسل DM، افتحها من الطرف الآخر، وتحقق من حالة القراءة.
5. احظر مستخدماً ثم جرّب إرسال رسالة جديدة من أي الطرفين؛ يجب منع الإرسال، ثم ألغِ الحظر.
6. قدّم بلاغاً وراجعه من لوحة المالك. جرّب حظر الحساب وإعادة تفعيله.
7. من حساب مشترك ارفع مشروعاً للبيع، وافق عليه من حساب المالك، تأكد من عدم إتاحة التحميل قبل grant، وجرّب منح صلاحية لمشترٍ بعد الدفع اليدوي.
8. عدّل مشروعاً كعضو ثم وافق على التعديل من حساب المالك، وحذف مشروع عضو آخر بصلاحية المالك.
9. بعد مرور 24 ساعة + دورة تشغيل للـWorker، افحص Cloudflare R2 وFirestore لتتأكد من حذف القصة وتفاعلاتها فعلياً.

## حدود موضحة بوضوح

- كل عضو مشترك يمكنه الاحتفاظ بحد أقصى **5 ستوريات نشطة**؛ الصورة حتى 2MB، فيديو MP4 حتى 12MB وبمدة 15 ثانية حسب بيانات الفيديو التي يفحصها الخادم.
- العدد الحالي للستوريات التي تُحمّل في الشاشة محدود لأول 100 قصة نشطة. أعداد مشاهدات/إعجابات القصص تُحسَب من سجلات تفاعل قد تصل إلى سقف العينة الحالي؛ عند ارتفاع الاستخدام ستحتاج تحسين الاستعلامات والفهارس.
- تنظيف الملفات بعد انتهاء 24 ساعة **ليس مضموناً في نفس الثانية**؛ الإخفاء يبدأ فور انتهاء صلاحية القصة، والحذف المادي في دورة التنظيف التالية عند عمل العامل واتصال الخدمات، أو لاحقاً وفق قاعدة R2 الاحتياطية. يستهلك هذا عمليات ضمن حصص Cloudflare وFirestore.
- Firebase Spark لا نستخدم معه Firestore TTL المدفوع؛ التنظيف بوساطة Cron Worker المجاني ضمن حدود Cloudflare.
- لا توجد مدفوعات إلكترونية تلقائية ولا مراسلات مشفرة طرفاً لطرف (E2EE). الرسائل الخاصة محمية بقواعد وصول للمشاركين، وتظل متاحة لمزوّد قاعدة البيانات وفق بنيته.
- تأكد من تكلفة الاستخدام عند نمو عدد القصص أو الملفات؛ الحصص المجانية ليست غير محدودة.

## نتائج المراجعة قبل النشر

- `npm test`: 43 اختبار JavaScript محلياً (نجحت جميعها عند إعداد الحزمة).
- محلّل TypeScript فحص نحوية `src/App.jsx` و`src/Community.jsx` والملفات البرمجية.
- **لم يتم تنفيذ بناء Vite كامل ولا الاختبار على Firebase/Cloudflare الحقيقيين** في هذه البيئة؛ لذلك يجب تنفيذ اختبارات النشر أعلاه قبل فتح المزايا الجديدة لجميع المستخدمين.

**الأهم:** لا تنشر الـWorker على نحو يلغي حماية المفتاح الإداري أو يسمح بأخذ مستخدمين آخرين من قاعدة البيانات. يحتاج العامل إلى قواعد `firestore.rules` الجديدة كي يمسح الوثائق المنتهية فقط.
